It visits chunks/scanlines rather than every pixel. Existing container validation remains responsible for CRC/order, and full Sharp/Images pixel decoding remains mandatory afterward.

**Why and options.** A Flowboard PNG may produce a viewable image despite carrying extra compressed or expanded data. The external decoder can recover silently, so successful output alone did not prove original bytes were complete and exact. A native decompression stream supplies the missing strict zlib boundary checks; small JS row accounting supplies the exact image-data shape. This avoids writing or maintaining another compression algorithm. Packed samples, filter prefixes and Adam7 pass extraction follow the [W3C PNG specification](https://www.w3.org/TR/png-3/). A full raw160MB pixel buffer would put a20MP RGBA16 image above a Worker isolate's memory allowance; draining and discarding native output avoids that JS allocation.
