# Clarification before implementation — original duplicate semantics remain

Before changing production source, Architect inspected existing `apps/api/test/import-repair.test.ts:119–151` and `:476–501`: an identical previously accepted row whose original status required a mapping must remain `already_imported` on reupload, without forcing a redundant mapping or overwriting the current card. This is the original IMP-08 contract, not a new exemption for malformed input.

The supplemental criteria.json sentence “duplicate-in-batch and assignee/status validation errors are never hidden by an old marker” was broader than that existing acceptance and is clarified here before implementation. Preserve every parser/source-field error (including invalid date/priority/numeric IDs) and duplicate-in-batch error even when the normalized hash matches a durable marker. For a source-valid identical previously accepted row, contextual current status/assignee checks may be superseded by a safe no-write duplicate skip; there is no new assignment or destination write to authorize. Changed valid original content must still conflict. Every actor/project/board authorization remains mandatory.

Implementation will retain a source-validation decision before adding context-dependent errors, and permit marker-based classification only for source-valid, nonduplicated rows. The original frozen import criteria, test counts, score floors and failed round3 records are unchanged. The reproduced malformed mixed-batch case must remain invalid and make zero new domain writes. This clarification preserves both the security fix and the existing mapped-row retry behavior; it does not discard the confirmed finding.
