# ATT-02 maximum-input blocker and design options

**Actions.** The current strict JPEG scan checker fails a mandatory valid-input case. `raw/jpeg-complexity-mounted.json` records two deterministic genuine5000×4000 progressive4:4:4 JPEGs: RGB9,434,300bytes and CMYK9,288,828bytes. Both are below10MiB/8192/20MP caps. A separate complete native decode/re-encode succeeds, draining58,005,364 and58,392,784 PNG bytes in1.79s/2.44s. Mounted Node and actual local workerd each return503 at~1.05–1.11s from the frozen checker budget. No image was saved. Exit0 for this diagnostic means evidence was collected; expected200 was not achieved. This is a release blocker, not an acceptable way to enforce20MP.

**Why and options.** In Flowboard, a valid photo must not become permanently impossible to attach merely because its pixels are complicated. The current checker preserves original bytes and rejects a known JPEG that both full decoders recover with a warning. Its cost and maintenance burden are now demonstrated. The options below are architectural choices, not source changes or approval.

The smallest viable next step is a parent architecture decision: if original input must be strictly valid and remain byte-identical, use a strict native runtime/decoder with adequate measured resources. If the product requirement is safely decodable stored image content, freeze an explicit canonical-output policy first, including how recovered input is treated. Current criteria are not changed merely to make a test pass.
