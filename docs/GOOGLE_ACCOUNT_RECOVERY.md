# Google account migration and recovery

Apply PostgreSQL migration `0030_google_account_subject.sql` before deploying the new API. The migration preserves existing users, grants, projects, sessions and email addresses. Existing users start with a blank Google binding because the former sign-in flow did not record Google's permanent account identifier. The new code checks the subject returned by Google's UserInfo endpoint after the server exchanges the authorization code. [Google OpenID Connect guidance](https://developers.google.com/identity/openid-connect/openid-connect)

## Existing sessions

A returning user with an eligible session can optionally open **Settings → Account → Confirm Google sign-in**. The browser starts the link with an explicit same-origin POST. Google prompts the user to choose an account and consent. Flowboard requires the same unexpired, unrevoked browser session at completion and a Google-verified email matching that account's stored address. The authorization code can only be redeemed with the per-attempt proof key. Account selection and consent may use an existing Google browser session. This flow proves continuity only as far as the prior Flowboard session is trustworthy. If there is evidence of an earlier takeover, use incident recovery and revoke affected credentials before treating any binding as trustworthy. [OAuth Security Best Current Practice](https://www.rfc-editor.org/rfc/rfc9700)

Existing unconfirmed users can keep using their boards and projects and sign in again with their usual verified address. Email-only sign-in requires exactly one matching account with no Google binding. It cannot attach a permanent Google ID. Keep the canonical Pages origin and Google callback registered consistently. In UAT, verify both the real Google sign-in flow and optional confirmation. OAuth attempts started before cutover can be restarted with the new version.

Once an account is confirmed, Flowboard rejects subsequent sign-ins from other Google identities that present that address. Any email-only sessions for the confirming account stop working at that point. Their browsers can sign in again with the confirmed identity. Other accounts continue to use their existing sessions. The compatibility path preserves ordinary sign-in, so an email address reassigned to someone else remains a security risk for an unconfirmed account.

## Optional recovery

An operator can assist only when independently verified evidence links the previous Flowboard user ID to Google's immutable subject and establishes that the person still controls that Google identity. One example is a trusted historical organization identity record that already maps the same immutable Google subject to the person behind the Flowboard account. Independently verify the historical Flowboard association as well as the present Google account. Current possession of a recycled address, an invitation link, or an old browser screenshot is insufficient. Where continuity cannot be established, keep the legacy account unbound. Project owners can issue fresh grants to a new account under its own identity if appropriate.

For an authorized recovery with that evidence, target the exact affected user ID in a reviewed parameterized database transaction. Lock the Google subject using the same subject advisory lock and take the user's quota lock before row mutations. Set the fixed `https://accounts.google.com` issuer and independently verified subject only where both identity fields are NULL, and require exactly one updated row. The unique database constraint rejects a subject already attached to another account. Preserve the email and grants during this operation. Revoke the account's existing Flowboard sessions in the transaction. Use the incident process to revoke other known-compromised credentials when applicable. Before committing, check the row count and verify the identity is attached to the intended user. Record the recovery ticket, operator and affected Flowboard user ID in the restricted operations record. Avoid recording provider tokens, browser cookies or raw invite tokens. There is no public endpoint for operator recovery.

## Email changes and invitations

The same verified Google subject can sign in after a change of email or domain. If its verified address is free, Flowboard updates the contact address and preserves the same actor and grants. If the address collides with another Flowboard account, Flowboard preserves the current actor and grants, retains the old displayed address and disables invitation actions that rely on that address. On the next successful sign-in with an available address, Flowboard resumes using the updated address. Settings shows the conflict.

Flowboard learns about an address change on the next successful Google login for that subject. Existing browser sessions then use the updated address or conflict status for invitation acceptance. A pending invitation is a separate single-use project grant to the address it was originally sent to. Once a verified address is reassigned, someone who controls that address and also obtains the still-pending token can accept it as that grant. Project administrators can revoke pending invitations and issue new ones to the intended address. A new account does not inherit earlier grants, projects, or sessions.

Rolling back to the old callback would remove the stable-identity check for confirmed accounts even with the new columns present. If the new provider flow must be withdrawn before a fix is ready, disable Google sign-in traffic until a secure build is available.
