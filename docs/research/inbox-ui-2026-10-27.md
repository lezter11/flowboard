# Inbox design research — 27 October 2026

## Direction

Flowboard's Inbox is a place to review work notifications and open their source, not a messaging or chat application. The design preview groups updates into Needs you, Updates and Access, offers search and read controls, and shows the selected item's context beside the list. On narrow screens the details follow the list. These categories explore possible future notification types; the approved notification contract currently covers mentions, and the preview does not establish other live delivery behavior.

## Decisions and sources

- Keep notification text short and help the user understand the next action. Atlassian's [information message guidance](https://atlassian.design/foundations/content/designing-messages/info-messages/) recommends relevant, direct messages that do not unnecessarily interrupt work.
- Present filter choices as buttons with state, not tabs without associated panels. See the [WAI-ARIA tabs pattern](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/) for the required relationships when actual tabs are used.
- Announce read and filter results without moving focus. [WCAG status messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html) explains the need to expose status changes to assistive technology.
- Respect reduced motion and keep a native scrolling fallback. See [MDN's reduced-motion guidance](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/%40media/prefers-reduced-motion). The local prototype uses vendored GSAP and Lenis; those files are not a production dependency decision.
- Do not put free-text search terms in URLs, because notification text may include project information. Preview filtering is local and is not a replacement for backend authorization.

## Boundaries

The screen uses synthetic fixture notifications and session-local read state. No notification is sent, no API is called, and the source-level project and board checks are not production access control. A real inbox must use the verified backend contract, enforce access on the server, and handle revoked access, loading, errors and pagination against real data. Visual and integrated verification are separate from this design exploration.
