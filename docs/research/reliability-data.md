# Flowboard reliability and performance checklist: data concerns 1–25

Researched 26 October 2026 (Asia/Kolkata). This report covers items 1–25 only. PostgreSQL is the recommended implementation baseline, with Cloudflare Workers as the initial portable runtime; the selected database host remains open. The existing D1 schema is a comparative/historical prototype. PostgreSQL plans below are proposals, not implemented features. Documentation establishes available behavior; it does not establish Flowboard's correctness, capacity, or deployment readiness.

## Evidence and decision frame

Reviewed `docs/ARCHITECTURE.md`, `docs/API.md`, `docs/DELIVERY.md`, `docs/VERIFICATION.md`, `database/README.md`, `database/prototypes/d1/migrations/0001_initial.sql` (moved after the initial inspection), and `scripts/check_schema.py`. Reran `python3 scripts/check_schema.py`: **11 tests passed against Python's in-memory SQLite**, with synthetic records only. This verifies selected local constraints and sequential rollback examples. It does not verify PostgreSQL, D1 `batch()`/`changes()`, concurrent requests, network failures, authentication, query plans, or performance. No application endpoints or database adapter exist yet.

Status meanings used below:

- **planned:** a design/control is specified but has no implementation evidence.
- **partial:** a schema or contract supports part of the concern; required runtime behavior remains absent.
- **verified-local:** a specifically named local test passed; no stronger conclusion follows.
- **deferred:** intentionally excluded from the initial deployment until its stated trigger.

Performance is the first decision criterion. Compare **the complete request path**, not database execution alone: browser region → application region → database/pool → SQL → serialization → response. Benchmark board load, paginated/filter reads, move, metadata edit, comment/mention, and concurrent edits on both the normal free-tier path and the first request after idle. Record p50/p95/p99, query count, bytes, pool/network/database time, conflicts, timeouts, and cost units. Agree representative workspaces/users/cards and latency objectives before treating any option as fast enough. No such benchmark exists today.

For a portable deployment, keep domain commands and HTTP contracts independent of cloud bindings; use one selected SQL adapter behind explicit transaction/query interfaces. PostgreSQL offers a conventional SQL transaction and driver boundary that can be hosted by different providers. A D1 adapter has different transaction and migration semantics and would need a deliberate migration; an ORM does not erase those differences. Keep clocks, identity, object storage, background delivery, and cache providers behind small interfaces. Avoid implementing two databases now. Hosting the same portable service near its PostgreSQL database on AWS/Azure later is an option, not proof of equivalent managed-service behavior or price.

An initial free-tier deployment should have one writer, bounded pages/payloads, measured indexes, and no mandatory Redis, read replica, or sharding tier. D1 currently publishes a 500 MB free per-database maximum, daily read/write allowances, and serial execution within each database; these are capacity constraints rather than throughput promises. A free PostgreSQL provider has separate connection/storage/compute/idle policies that must be checked after a provider is selected. **There is no verified free PostgreSQL hosting choice or measured winner in this report.** [D1 limits](https://developers.cloudflare.com/d1/platform/limits/), [D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/)

## 1. Race Conditions

- **Explanation and applicability:** Two requests act on state that changes between reading and writing. Relevant immediately to simultaneous card moves, invite acceptance, membership revocation, owner transfer, and duplicate notification work.
- **Design plan:** PostgreSQL: make state checks and mutations one transaction, use conditional version updates, and lock a shared board/membership row where a cross-row invariant requires coordination. Membership-removal and write commands must share a locking/check protocol if the product promises immediate revocation; a preflight check alone is insufficient. D1: include permission/version gates and dependent writes in one atomic batch; an UPDATE affecting zero rows is successful SQL, so force failure or gate subsequent event/outbox/receipt writes.
- **Evidence required:** Real concurrent connections/requests synchronized at the read/write boundary; two moves with one expected revision, move versus revoke, one-use invite races, and retried requests after lost responses. Assert final state and exact side-effect count. **Current status:** **partial**; versions and gates are specified. **Verified-local subset:** sequential valid/stale/revoked guard examples pass; this is not a race test.
- **Adoption trigger and pitfall:** Controls are required before the first shared-user release. Do not assume JavaScript's single thread, SQLite serialization, or a successful transaction prevents application-level stale decisions. [PostgreSQL isolation](https://www.postgresql.org/docs/current/transaction-iso.html), [D1 batch](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)

## 2. Deadlocks

- **Explanation and applicability:** Transactions hold resources that one another needs, forming a wait cycle. Relevant to PostgreSQL moves, membership administration, outbox workers, and migrations.
- **Design plan:** PostgreSQL: acquire shared resources in one documented order, such as membership/workspace guard → ordered board IDs → ordered card IDs; keep transactions short. Use operation-scoped lock/statement deadlines and bounded whole-transaction retries for deadlock/serialization failures where safe. D1 does not expose PostgreSQL row-lock transactions; prioritize short batches and overload/retry handling rather than copying `FOR UPDATE` syntax.
- **Evidence required:** A deliberately reversed two-connection lock test proving one transaction aborts and the command safely retries; monitor wait time and deadlock counts. Verify cancellation releases the transaction/client. **Current status:** **planned**; no PostgreSQL adapter, lock ordering implementation, deadlines, or deadlock tests.
- **Adoption trigger and pitfall:** Define the protocol when implementing multi-row PostgreSQL commands, not after incidents. `SELECT` statements may participate in locking behavior; do not hold a transaction open while waiting for a user or external API. PostgreSQL detects deadlocks and aborts a participant; this does not perform application retry for us. [Explicit locking and deadlocks](https://www.postgresql.org/docs/current/explicit-locking.html), [timeouts](https://www.postgresql.org/docs/current/runtime-config-client.html#GUC-LOCK-TIMEOUT)

## 3. Database Transactions

- **Explanation and applicability:** A transaction commits a group of database operations together or cancels them together. Immediate for card + revision + activity + outbox + receipt, workspace + owner membership, and comment + mentions.
- **Design plan:** PostgreSQL: expose domain-level transaction functions using one checked-out connection for the full transaction, with commit/rollback and release in cleanup. Avoid generic `pool.query()` calls for a transaction spread across arbitrary clients. D1: compile the guarded command into one `batch()`; do not place `BEGIN` and `COMMIT` around separate awaited D1 calls. External email, object storage, sockets, and queues are outside either database's atomic transaction; insert outbox intent first and deliver afterward.
- **Evidence required:** Inject a failure after every statement; assert no half-written card, orphan mention, event, receipt, or notification intent. Test uncertain commit after connection loss through idempotent retry. **Current status:** **partial**; schema/contract present. **Verified-local subset:** later-constraint-failure rollback passes in SQLite; the actual transaction adapter is absent.
- **Adoption trigger and pitfall:** Required in the first mutation implementation. A database rollback cannot recall a previously sent email. [PostgreSQL transactions](https://www.postgresql.org/docs/current/tutorial-transactions.html), [node-postgres transactions](https://node-postgres.com/features/transactions), [D1 batch](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)

## 4. ACID Properties

- **Explanation and applicability:** Atomicity means all-or-nothing; consistency means declared invariants remain valid; isolation controls concurrent visibility; durability concerns committed data surviving failure. All four matter immediately, but they are separate properties.
- **Design plan:** PostgreSQL: combine transactions with correct constraints and concurrency protocols; keep durability settings appropriate to real data, and verify the chosen host's backup/failover guarantees. D1: use documented atomic batches, constraints, and recovery facilities; verify its deployed behavior independently of local SQLite. Neither engine automatically knows the business rule “exactly one active owner,” nor does ACID cover external integrations.
- **Evidence required:** Fault/rollback tests for atomicity; invariant tests for consistency; real concurrency tests for isolation; restart/failure and restore exercises against an isolated target for durability/recovery. Record recovery-point/time objectives separately; a successful backup command is not a restore test. **Current status:** **partial**; several constraints and local rollback examples exist. No durability/failover or restore evidence.
- **Adoption trigger and pitfall:** Required before storing real team data. Do not disable durability to win a benchmark and then compare that result to production-safe settings. [PostgreSQL transactions](https://www.postgresql.org/docs/current/tutorial-transactions.html), [PostgreSQL reliability](https://www.postgresql.org/docs/current/wal-reliability.html), [D1 recovery limits](https://developers.cloudflare.com/d1/platform/limits/)

## 5. Isolation Levels

- **Explanation and applicability:** Isolation determines whether repeated reads inside a transaction can see different committed state and which concurrent anomalies are possible. Immediate for a consistent board snapshot and cross-row rules.
- **Design plan:** PostgreSQL: default short mutations to Read Committed **with explicit CAS/locking/invariants**. A multi-statement board snapshot needs Repeatable Read/read-only or a deliberately single-statement query; simply putting its SELECTs in a Read Committed transaction is insufficient. Consider Serializable for complex invariants only with whole-transaction retries and measurements. D1 offers its API transaction/session consistency model, not configurable PostgreSQL isolation levels; use one primary batch for the promised bounded snapshot and revalidate commands.
- **Evidence required:** Two-session tests for changed rows/phantoms/write skew; snapshot queries while another session moves/edits cards. Verify any Serializable retry begins a fresh transaction and never repeats an external side effect. **Current status:** **planned** for PostgreSQL; the canonical snapshot contract exists but no implementation proves it.
- **Adoption trigger and pitfall:** Choose isolation per command/query when the SQL adapter is built. PostgreSQL Read Uncommitted behaves as Read Committed; Repeatable Read is not equivalent to Serializable. [PostgreSQL isolation levels](https://www.postgresql.org/docs/current/transaction-iso.html), [D1 sessions/batch](https://developers.cloudflare.com/d1/worker-api/d1-database/)

## 6. Optimistic Locking

- **Explanation and applicability:** Send the version last read and update only if it still matches. It avoids waiting on a lock during user editing and detects lost updates. Immediate for cards, comments, and ordering.
- **Design plan:** PostgreSQL: `UPDATE ... WHERE tenant/id/version ... RETURNING ...`, increment the row revision, and require exactly one affected row before recording effects. Keep card version, board order/configuration revision, and snapshot/filter revision distinct. D1: the same logical CAS, with an immediate constraint-backed guard inside the batch. Recheck a conflict through an authorized read; the client must not invent a newer version and overwrite another edit automatically.
- **Evidence required:** Same-version concurrent updates, stale move after metadata edit, absent/deleted objects, permission changes, and rank compaction. Assert versions and receipts roll back together. Measure conflict/retry rate under realistic collaboration. **Current status:** **partial**; versions, snapshot version and guards exist in schema/docs. **Verified-local subset:** sequential stale guard rollback passes. No HTTP conflict behavior.
- **Adoption trigger and pitfall:** Implement immediately. Board-wide ordering CAS is simple but rejects unrelated moves; only narrow it to per-column coordination after measured contention justifies added complexity. [PostgreSQL UPDATE](https://www.postgresql.org/docs/current/sql-update.html), [D1 batch](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)

## 7. Pessimistic Locking

- **Explanation and applicability:** Lock a row before computing a change, making competing writers wait. Useful inside short server transactions, not across a user's edit session.
- **Design plan:** PostgreSQL: use a board coordination row for rank calculations/rebalance and a workspace/membership guard for ownership/revocation invariants. Keep optimistic client versions so waiting does not silently overwrite old user intent. Use `FOR UPDATE SKIP LOCKED` only where skipping busy rows is acceptable, such as claiming independent outbox jobs; not for a complete user-facing board snapshot. D1: no equivalent exposed interactive row-lock protocol; retain guarded batches. A future Durable Object coordinator does not make D1 + object writes one transaction.
- **Evidence required:** Two writers on one board versus independent boards; lock wait/cancellation; lease recovery after worker death; no skipped user data. **Current status:** **planned** for PostgreSQL; D1 alternative documented, neither implemented.
- **Adoption trigger and pitfall:** Adopt for commands whose invariant cannot be kept by one conditional write; measure hot-board waiting. Adding locks everywhere can reduce free-tier throughput. [PostgreSQL locking](https://www.postgresql.org/docs/current/explicit-locking.html), [SKIP LOCKED limitations](https://www.postgresql.org/docs/current/sql-select.html#SQL-FOR-UPDATE-SHARE)

## 8. Connection Pooling

- **Explanation and applicability:** Reuse a bounded set of database connections instead of performing a full connection/authentication handshake for every query. Immediate if choosing PostgreSQL.
- **Design plan:** PostgreSQL on a persistent Node service: one bounded pool per process, not per request, with acquisition timeout and release in cleanup. Total connections across instances/jobs/migrations must fit the provider's budget. On Cloudflare Workers, evaluate Hyperdrive's pool with request-local database clients and query caching disabled for fresh collaboration/auth data. Treat these as different runtime adapters. D1 bindings require no application-maintained TCP pool.
- **Evidence required:** Burst and sustained load, pool acquisition time, free-provider connection cap, leaked-client failure, cold/idle resume, and cancellation. Test transaction-local tenant settings with transaction pooling; never assume session state survives reassignment. **Current status:** **planned**; no connection settings, provider, credentials, or measured pool.
- **Adoption trigger and pitfall:** Required at PostgreSQL integration. Increasing pool size can worsen memory/CPU contention. Pooling reduces setup cost; it does not remove all application-to-database round trips or solve slow SQL. [node-postgres pooling](https://node-postgres.com/features/pooling), [Hyperdrive connection lifecycle](https://developers.cloudflare.com/hyperdrive/concepts/connection-lifecycle/), [pool tuning](https://developers.cloudflare.com/hyperdrive/configuration/tune-connection-pool/)

## 9. N+1 Queries

- **Explanation and applicability:** Fetch N cards, then make one extra query per card for assignees/comments. Query count grows with the page and network latency multiplies it. Immediate board/list performance risk on either database.
- **Design plan:** Fetch a bounded parent page, then batch related assignee/member/label data for those IDs, or use measured joins/aggregation. Return comment counts rather than every comment on a board card. D1 can batch prepared statements but batching N statements still does N database operations; a batched relation query is preferable when appropriate. Respect parameter limits by bounding/chunking IDs. Keep authorization predicates in batched queries.
- **Evidence required:** Assert query count remains bounded when page size increases; compare bytes, rows and latency for sparse/dense relationships. Verify pagination limits parent cards before joining children to avoid duplicate parents/truncated lists. **Current status:** **planned**; bounded API pages are specified, no actual query implementation exists.
- **Adoption trigger and pitfall:** Prevent during the first board/read adapter. Replacing N+1 with a giant multi-relation join can multiply result rows and become slower; measure both shapes. [PostgreSQL joins/table expressions](https://www.postgresql.org/docs/current/queries-table-expressions.html), [D1 parameter limits](https://developers.cloudflare.com/d1/platform/limits/)

## 10. Database Indexes

- **Explanation and applicability:** Indexes help locate/sort relevant rows without scanning all data, at the cost of storage and extra work on writes. Immediate for tenant-scoped board pages, comments, memberships, inbox, and outbox claims.
- **Design plan:** PostgreSQL: start with measured B-tree access paths aligned to equality scope and stable cursor order; evaluate partial active-card/pending-outbox indexes. Include referencing foreign-key columns where delete/update workloads need them. D1: retain appropriate SQLite composite/partial indexes; track scanned and written rows. Existing schema examples include card order, due dates, comment/activity cursors, membership lookup and pending outbox.
- **Evidence required:** Representative plans before/after each proposed index, rows/buffers, read/write latency, index size, and maintenance overhead. Test filters independently; an index name is not proof the query uses it. **Current status:** **partial**; indexes exist in the SQLite schema, but no index workload has been benchmarked.
- **Adoption trigger and pitfall:** Basic indexes accompany implementation; add specialized ones after plan evidence. Do not index every field or assume a composite index serves every column subset equally well. [PostgreSQL multicolumn indexes](https://www.postgresql.org/docs/current/indexes-multicolumn.html), [partial indexes](https://www.postgresql.org/docs/current/indexes-partial.html), [D1 indexes](https://developers.cloudflare.com/d1/best-practices/use-indexes/)

## 11. Query Optimization

- **Explanation and applicability:** Reduce avoidable work and round trips while preserving the exact API result. Highest-priority initial performance work.
- **Design plan:** PostgreSQL and D1: bound cards, columns and related data; project needed fields; use keyset cursors with `(position,id)` or `(created_at,id)`; filter by tenant/board early; separate expensive counts/search when product semantics allow. Profile application/network time before rewriting SQL. PostgreSQL adds planner statistics and buffer/I/O analysis; D1 adds rows-read/write metadata and serial-database queueing concerns. A “bounded first page per column” still needs a maximum/paginated column scope to remain bounded for very wide boards.
- **Evidence required:** Seed realistic skew (one large workspace/board, many tiny boards, dense assignees), execute every supported filter/sort, save plans and p95/p99. Profile count queries and `%substring%` title search; a normal B-tree does not automatically solve arbitrary substring search. **Current status:** **planned**; API pagination and indexes are partial foundations, no query or latency evidence.
- **Adoption trigger and pitfall:** Optimize the measured critical path before caches/replicas. A sequential scan can be the correct plan for a tiny table or a query returning most rows. [PostgreSQL query plans](https://www.postgresql.org/docs/current/using-explain.html), [D1 indexes](https://developers.cloudflare.com/d1/best-practices/use-indexes/)

## 12. EXPLAIN ANALYZE

- **Explanation and applicability:** PostgreSQL `EXPLAIN` shows an estimated execution plan; `EXPLAIN ANALYZE` executes the query and reports actual work/timing. Required evidence for performance claims.
- **Design plan:** PostgreSQL: capture `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` for representative read queries in an isolated seeded database; inspect estimates versus actual rows, loops, sort spill, and buffer work. Record end-to-end request latency separately. D1/SQLite: use `EXPLAIN QUERY PLAN` and runtime metadata; this is not PostgreSQL's execution instrumentation, and SQLite `ANALYZE` updates statistics rather than meaning “run EXPLAIN ANALYZE.”
- **Evidence required:** Save query shape/parameters, engine/version, data size/distribution, warm/cold conditions, and before/after plans. Query plans for empty fixture tables are weak performance evidence. **Current status:** **planned**; no saved plans or query benchmarks.
- **Adoption trigger and pitfall:** Use when implementing important reads and whenever they regress. `ANALYZE` actually executes writes/functions too; do not run mutation plans against real data casually. SQLite plan text can change, so avoid brittle exact-output tests. [PostgreSQL EXPLAIN](https://www.postgresql.org/docs/current/using-explain.html), [SQLite EXPLAIN QUERY PLAN](https://www.sqlite.org/eqp.html)

## 13. Foreign Key Constraints

- **Explanation and applicability:** A foreign key prevents a row from referring to a nonexistent or incompatible parent. Immediate for cards/columns/boards, membership-backed assignees, comments, and notifications.
- **Design plan:** PostgreSQL: port the composite tenant/board foreign keys and deliberate deletion policies, not merely each global ID relationship. Add useful indexes on referencing columns; PostgreSQL does not automatically create those indexes. D1: preserve its enforced foreign keys and use documented deferred-check migration behavior when necessary. Neither engine's FK proves active membership/role or performs API authorization. Keep historical membership rows for retained authors/events.
- **Evidence required:** Cross-workspace and same-workspace/wrong-board rejection; missing parent and retained-history deletion cases; migration validation and FK consistency checks on the selected engine. **Current status:** **verified-local** for the specific SQLite reference tests; **partial** overall. No PostgreSQL/D1 integration evidence. Archived cards still prevent column deletion.
- **Adoption trigger and pitfall:** Required in the initial schema. Avoid broad cascades that accidentally erase audit/history. Null components can bypass composite FK checking unless nullability/match rules are deliberately chosen. [PostgreSQL foreign keys](https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-FK), [D1 foreign keys](https://developers.cloudflare.com/d1/sql-api/foreign-keys/)

## 14. Unique Constraints

- **Explanation and applicability:** The database rejects duplicates even when two requests race past application checks. Immediate for identity subjects, memberships, assignments, receipts and one notification per event/recipient.
- **Design plan:** PostgreSQL: enforce scoped composite unique keys and the partial at-most-one-active-owner index. D1: retain equivalent supported uniqueness constraints. Keep receipt keys non-null and store a request hash. Order ranks need deterministic ties or a separate collision protocol; adding a unique rank index changes rebalance mechanics and cannot be an unexamined optimization.
- **Evidence required:** Duplicate insert races on the selected engine, authorized replay of the winning receipt, distinct scopes, and normalized identity/invite cases. Assert the operation rolls back rather than committing domain state without its receipt. **Current status:** **verified-local** for tested SQLite assignment, owner, notification and receipt duplicates; **partial** for full replay and concurrency semantics.
- **Adoption trigger and pitfall:** Required initially. A partial owner index ensures **at most one**, not **at least one**; owner removal/transfer needs an atomic command. An application “SELECT first, INSERT later” does not replace uniqueness. [PostgreSQL unique constraints](https://www.postgresql.org/docs/current/ddl-constraints.html#DDL-CONSTRAINTS-UNIQUE), [partial indexes](https://www.postgresql.org/docs/current/indexes-partial.html)

## 15. Database Migrations

- **Explanation and applicability:** Ordered, reviewed schema/data changes transform an existing database without losing the meaning of its data. Immediate before remote setup.
- **Design plan:** PostgreSQL: maintain a selected-engine migration history and one controlled runner per environment, using transactions where statements support them. Port SQLite-specific types/functions/checks explicitly; date, JSON, parameter syntax and `changes()` need real changes. D1: versioned Wrangler SQL migrations with explicit database/environment targets. Keep schema and application release compatibility recorded, not inferred from a deployment success.
- **Evidence required:** Apply from empty and from each supported previous schema; rehearse with realistic synthetic volume; inject failure and inspect migration ledger/data. Capture backup and restore into an isolated target before destructive operations. **Current status:** **partial**; one SQLite migration applies locally. No managed database migration, runner, environment bindings, or PostgreSQL migration exists.
- **Adoption trigger and pitfall:** Required before the first remote database. Do not blindly wrap every PostgreSQL migration in one transaction: concurrent index creation is an exception. Rolling back application code does not reverse committed data/schema. [D1 migrations](https://developers.cloudflare.com/d1/reference/migrations/), [PostgreSQL CREATE INDEX](https://www.postgresql.org/docs/current/sql-createindex.html)

## 16. Zero-Downtime Migrations

- **Explanation and applicability:** Evolve schema while old/new application versions and live writes may coexist. An operational goal with workload-specific limits, not a property of a migration tool.
- **Design plan:** PostgreSQL: expand → deploy compatible code → batched/resumable backfill → validate → contract in a later release. Assess each DDL lock; use concurrent index builds or deferred validation where supported, with bounded lock acquisition and a recovery path for failed/invalid indexes. D1: also use additive compatibility and bounded backfills, but do not copy PostgreSQL's concurrent-DDL syntax or promise no interruption for a table rebuild.
- **Evidence required:** Run old/new readers and writers during a rehearsal, measure blocked requests and lock waits, resume an interrupted backfill, and verify rollback compatibility. Test at representative volume. **Current status:** **planned**; expand/migrate/contract is documented only.
- **Adoption trigger and pitfall:** Required before changing a live shared deployment. “CONCURRENTLY” does not mean no resource use or no lock/wait; PostgreSQL cannot run `CREATE INDEX CONCURRENTLY` inside a transaction block. [CREATE INDEX concurrency](https://www.postgresql.org/docs/current/sql-createindex.html#SQL-CREATEINDEX-CONCURRENTLY), [ALTER TABLE/validation](https://www.postgresql.org/docs/current/sql-altertable.html)

## 17. Read Replicas

- **Explanation and applicability:** Read-only database copies can offload reads or place eligible data closer to readers. They do not add independent write capacity to the primary.
- **Design plan:** PostgreSQL: begin with one writer/reader endpoint. Later route explicitly stale-tolerant analytics to replicas; use the writer for authorization, sessions, commands, and fresh post-write board reads. D1: begin on primary; read replication requires its Sessions API to use replicas, with application bookmark handling. Keep routing explicit in the repository adapter rather than hiding it in arbitrary ORM choices.
- **Evidence required:** Primary/replica routing tests, measured lag under writes, failure/fallback behavior, and a comparison showing net p95 benefit after network and consistency costs. **Current status:** **deferred**; no replica exists or is configured.
- **Adoption trigger and pitfall:** Add only when optimized reads measurably saturate the writer or user-region latency justifies it and the selected plan supports it. A spare failover database is not automatically a read-serving replica; regional copies and backups are different concepts. [PostgreSQL hot standby](https://www.postgresql.org/docs/current/hot-standby.html), [D1 read replication](https://developers.cloudflare.com/d1/best-practices/read-replication/)

## 18. Replication Lag

- **Explanation and applicability:** A replica may not yet contain a write the primary acknowledged. Immediate design concern if replicas are adopted, otherwise a deferred runtime feature.
- **Design plan:** PostgreSQL: primary-stick fresh reads or implement an explicit replication-position wait/fallback policy; a guessed short sleep is not a correctness guarantee. Monitor replay progress and query cancellation behavior. D1: carry the latest session bookmark across the relevant logical user flow; bookmarks enforce session sequencing, not universal real-time freshness for every other user's session. Keep revocation checks primary even if ordinary list reads can be stale.
- **Evidence required:** Induce lag with controlled workload, write then read from another region, revoke membership during lag, and prove timeout fallback. Distinguish idle-replica metrics from actual freshness rather than treating an old replay timestamp as automatic failure. **Current status:** **deferred**; no lag metrics or read-routing implementation.
- **Adoption trigger and pitfall:** Must be implemented with item 17. Returning an apparently successful old board immediately after a move undermines trust; increasing replica count does not fix this consistency issue. [PostgreSQL standby conflicts](https://www.postgresql.org/docs/current/hot-standby.html), [replication statistics](https://www.postgresql.org/docs/current/monitoring-stats.html#MONITORING-PG-STAT-REPLICATION-VIEW), [D1 consistency/bookmarks](https://developers.cloudflare.com/d1/best-practices/read-replication/)

## 19. Database Sharding

- **Explanation and applicability:** Split data among independently writable databases using a routing key. This scales/isolate workloads but makes cross-shard transactions, joins, uniqueness and operations harder.
- **Design plan:** PostgreSQL: retain `workspace_id` in tenant-owned keys and keep ordinary commands within one workspace, but start on one database. If needed, introduce a workspace→shard directory and controlled tenant migration; global identities and actor-global receipts need an explicit home. D1: multiple smaller tenant databases are a documented scale-out option, but provisioning, routing, migration fan-out, and cross-workspace inbox/identity queries become application responsibilities.
- **Evidence required:** Tenant-routing isolation tests, move/cutover rehearsal, consistent receipt routing during a move, missing-shard recovery, and backup/restore per shard. Benchmark first to show sharding addresses the limiting resource. **Current status:** **deferred**; tenant keys are a partial prerequisite, no shard infrastructure.
- **Adoption trigger and pitfall:** Only after one appropriately sized, optimized database cannot meet capacity/isolation needs or a tenant requires dedicated placement. PostgreSQL table partitioning is not automatically multi-server write sharding. D1 free database-count/storage quotas still apply. [D1 scale-out limits](https://developers.cloudflare.com/d1/platform/limits/), [PostgreSQL partitioning scope](https://www.postgresql.org/docs/current/ddl-partitioning.html)

## 20. Partitioning

- **Explanation and applicability:** Split a logical table into smaller pieces, often by time or key. Useful for very large history tables and retention; usually unnecessary for an initial small Kanban database.
- **Design plan:** PostgreSQL: consider time partitioning for activity/history only after plans and retention costs justify it. Ensure queries include the partition key and arrange future partitions before writes arrive. Review uniqueness/FKs before changing keys: a partitioned table's unique/primary-key constraints must include partition keys under PostgreSQL's rules. D1: do not assume PostgreSQL declarative partitioning; manual table splitting adds query/migration complexity, while database-per-tenant is a different design.
- **Evidence required:** Plan shows pruning, retention/drop rehearsal, inserts at time boundaries and missing-partition failure, plus primary/foreign-key compatibility and metadata/plan overhead. **Current status:** **deferred**; ordinary indexed tables only.
- **Adoption trigger and pitfall:** Large append-only tables or slow retention/maintenance despite good indexes. Partitioning small card tables can add work without improving reads, and dropping an activity partition must not orphan retained notification/outbox references. [PostgreSQL declarative partitioning and limitations](https://www.postgresql.org/docs/current/ddl-partitioning.html)

## 21. Cache Invalidation

- **Explanation and applicability:** Stop serving a cached answer after its source or permission changes. Relevant to browser query state now and optional server/shared caches later.
- **Design plan:** Both engines: initially return authenticated API data as private/no-store; invalidate/refetch affected browser board/card/comment queries after a committed mutation. Board `snapshot_version` changes on filter-affecting edits; `structure_version` remains the order/configuration guard. For later shared data caching, use tenant+authorization scope, projection/schema version and source revision in keys, short bounded TTLs, and outbox-driven invalidation. Authorize before serving private cached data. Hyperdrive query caching must be explicitly disabled for these reads: it does not purge cached SELECTs on writes.
- **Evidence required:** Read→edit→read, membership revoke, concurrent miss/fill versus invalidation, lost invalidation recovery, and cross-tenant key collision tests. **Current status:** **planned**; version/no-store rules exist, no browser or shared cache implementation.
- **Adoption trigger and pitfall:** Browser invalidation is required with the first UI. Shared caching needs measured benefit; deleting a key after commit alone can race with an older in-flight fill, so it is not a proof of freshness. [Azure cache-aside consistency](https://learn.microsoft.com/en-us/azure/architecture/patterns/cache-aside), [Hyperdrive cache behavior](https://developers.cloudflare.com/hyperdrive/concepts/query-caching/)

## 22. Redis Eviction

- **Explanation and applicability:** Redis can remove keys under memory pressure according to a policy. Expiration and eviction are different: TTL is not a promise a key will remain available until then.
- **Design plan:** PostgreSQL and D1 remain authoritative; Redis is optional disposable cache only. If adopted, set a memory budget and choose an all-keys LRU/LFU policy using measured access patterns, or deliberately use noeviction and handle failed writes. Separate correctness-critical records from evictable cache; keep receipts, canonical sessions/revocation and durable outbox in SQL. Account for connection/buffer/replication memory beyond the cache dataset and free-plan feature restrictions.
- **Evidence required:** Fill the selected service to its limit; inspect eviction, rejected writes, hit rate and database surge. Verify all cache misses/failures preserve correctness and bound database fallback. **Current status:** **deferred**; Redis is not a prerequisite and no Redis instance exists.
- **Adoption trigger and pitfall:** Only when repeated cacheable reads justify the extra service, network hop and operations budget. LRU/LFU are approximate policies; volatile-only eviction can have no eligible victim if keys lack TTLs. [Redis key eviction](https://redis.io/docs/latest/develop/reference/eviction/)

## 23. Cache Stampedes

- **Explanation and applicability:** Many clients miss or expire the same hot key and simultaneously regenerate it, overloading the database. A cache can make the uncached path less frequently exercised and more fragile.
- **Design plan:** Either database: do not add an initial shared cache solely to solve this hypothetical problem. When introduced, use request coalescing, jittered expirations, bounded regeneration concurrency, and stale-while-refresh only for data whose staleness is allowed. Per-process coalescing only protects that process/isolate; multi-instance regeneration needs a deliberate shared lease/coordinator and bounded wait/fallback. Never use stale membership as an availability shortcut.
- **Evidence required:** Synchronized hot-key expiry, cold deployment, cache flush/outage, a slow/dead refresher, and negative-result bursts; measure peak database QPS and queue/wait time. Verify stale refresh cannot replace a newer version. **Current status:** **deferred**; no cache/refresh mechanism exists.
- **Adoption trigger and pitfall:** Implement before enabling a high-hit-rate shared cache on an expensive hot query. TTL jitter alone does not prevent a single popular key from stampeding; a lease's expiration also does not establish database write ownership. [AWS caching challenges/coalescing](https://aws.amazon.com/builders-library/caching-challenges-and-strategies/)

## 24. Distributed Caching

- **Explanation and applicability:** Multiple app instances share reusable cached answers. This reduces duplicate reads but adds a network dependency, staleness rules, tenant scoping, serialization and outage behavior.
- **Design plan:** PostgreSQL or D1: begin without a distributed cache. If measured later, use a small cache interface, versioned serializable values and namespace/environment/workspace/scope keys. Keep it replaceable across clouds. Cache only results with an explicit freshness allowance; implement short connection/time budgets, bounded fallback, and load shedding. Redis client-side tracking is an additional local-cache consistency mechanism; a disconnected invalidation channel requires discarding/revalidating local state, not assuming it remains fresh.
- **Evidence required:** End-to-end hit/miss latency against direct SQL, cache disabled/outage load, reconnection, mixed schema versions, cross-tenant tests, and hit-rate/memory measurements. **Current status:** **deferred**; browser query-state planning is not distributed cache evidence.
- **Adoption trigger and pitfall:** A shared, repeated, expensive read with demonstrable net latency/cost improvement after indexing and batching. Do not turn in-process Worker memory into an authoritative shared cache or assume a remote cache is faster than a nearby indexed database. [AWS cache tradeoffs](https://aws.amazon.com/builders-library/caching-challenges-and-strategies/), [Redis client-side cache invalidation](https://redis.io/docs/latest/develop/reference/client-side-caching/)

## 25. Idempotency

- **Explanation and applicability:** Retrying the same operation produces one logical result instead of repeating the business effect. Immediate because clients cannot reliably know whether a timed-out write committed.
- **Design plan:** PostgreSQL: atomically write domain changes, activity/outbox and a unique actor+scope+key receipt containing method/path/body hash and canonical result. Race losers roll back and read the winner through a fresh authorized transaction; the same key with different input conflicts. Use actor-global receipts before a workspace exists; logout can remain inherently idempotent. D1: the same receipt semantics inside a guarded batch, using the existing two receipt tables. Retain for an explicit retry window and document that expired keys may become new commands. External deliveries require their own deduplication keys/outbox state; SQL receipts do not make external providers exactly-once.
- **Evidence required:** Concurrent duplicate requests, altered payload/key reuse, cross-actor/workspace scopes, lost response after commit, failure before/after receipt, expiration cleanup, removed access on replay, and duplicate outbox delivery. **Current status:** **partial**; receipt tables and API policy exist. **Verified-local subset:** scoped/global receipt uniqueness passes; no HTTP replay or uncertain-commit test.
- **Adoption trigger and pitfall:** Required in the first mutation endpoint and dispatcher. Caching an idempotency key only in Redis risks duplicate effects after eviction; storing a receipt after a separate domain commit leaves a duplicate window. [PostgreSQL transactions](https://www.postgresql.org/docs/current/tutorial-transactions.html), [D1 atomic batches](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch), [queue duplicate-delivery contract](https://developers.cloudflare.com/queues/reference/delivery-guarantees/)
