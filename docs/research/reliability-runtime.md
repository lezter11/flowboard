## Recommended starting point

Start with one application/API, one canonical transactional database, bounded requests, revision-checked writes, idempotency receipts, foreground polling, and a small durable outbox dispatcher for mentions. Keep that deployment small until measurements justify another component. A managed queue, event bus, distributed cache, service mesh, Kubernetes cluster, separate read database, and cross-cloud active/active deployment are not prerequisites for a collaborative board.

Measure representative board reads, card moves, comment/mention creation, concurrent edits on one busy board, and reconnect polling. Record p50/p95/p99 latency, cold versus warm requests, error/conflict rate, database round trips, scanned rows, CPU time, connection/concurrency use, payload size, and queue/outbox age. Test near the intended users and database region. An edge API with several sequential calls to a distant primary can be slower than a regional API close to that database; compare the actual paths rather than equating geographic distribution with low latency.

Suggested initial experiments use 500 cards, 50 members, and 10 concurrent editors, then a burst at several times the expected traffic. These are **test fixtures, not supported capacity claims**. The architect should agree latency and notification-lag targets before declaring a winner. Do not let a free allowance hide poor p95 performance, weak transaction semantics, or an unrehearsed recovery path.

### Portable boundaries

| Boundary | Portable contract | Provider-specific responsibility |
| --- | --- | --- |
| Commands and queries | Domain validation, authorization, revision rules, input/output schemas, idempotency semantics | HTTP entry point and selected storage adapter |
| Atomic commands | Commit card/comment, activity, receipt and outbox together or none | D1 guarded batches versus PostgreSQL transactions/locking; prove each separately |
| Deferred work | Versioned event IDs, handler, retry classification, lease/fencing semantics, deduplication | SQL job polling or Cloudflare Queues/SQS/Azure queue adapter |
| Scheduling | Invoke a bounded `drainDueWork` operation | Workers Cron, EventBridge Scheduler, Azure timer/job scheduler |
| External calls | Deadline, cancellation, retry budget, response classification | Fetch/SDK runtime adapter; account for SDK retries |
| Telemetry | Request/operation/event IDs, metrics names, W3C trace context | Exporter, credentials, sampling and runtime flush behavior |

Use domain-level operations rather than a generic transaction callback that pretends every database supports the same transaction model. SQLite-to-PostgreSQL migration is real SQL/data/constraint work. A container image does not automatically run as an edge Worker; keep a Worker entry adapter and, if needed later, a Node/container adapter around the same tested domain contracts.

## 26. Retry Mechanisms

- **Meaning and decision.** Retry a transient failed attempt; do not repeat a permanent failure or silently reissue a changed command. The performance risk is multiplying downstream work while it is already overloaded. AWS recommends bounded retries and accounting for retries already built into SDKs. [AWS retry guidance](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_mitigate_interaction_failure_limit_retries.html) **Plan.** Give one layer ownership of retrying each dependency call. Prototype at most two retries within an interactive command's total deadline. Retry selected network failures, 429 and transient gateway/service failures only when the operation is safe. Writes reuse the exact idempotency key and body because a timeout does not prove the first commit failed. Do not retry 400/401/403/404/422 or a 409 stale version automatically; reconcile first. Retry a known database serialization conflict only by rereading/revalidating the whole transaction under a separate bounded rule, never by changing a user command's expected version blindly.
- **Current status.** API retry/idempotency rules are documented; receipt tables exist. No request client or API replay implementation is verified. **Adoption trigger.** Required with the first networked API and dependency client; no new infrastructure is needed.
- **Acceptance evidence.** Inject failure before commit, after commit/before response, and permanent validation failure. Demonstrate one card/comment/event/notification outcome, unchanged command payload, bounded attempt count, cancellation, and no retry multiplication across browser/API/SDK.

## 27. Exponential Backoff

- **Meaning and decision.** Increase the delay between retry attempts so failed traffic does not keep hitting a dependency at full speed. Backoff is useful only with a cap, attempt budget and request deadline. [AWS: timeouts, retries and backoff](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/) **Plan.** A proposed interactive starting policy is a 250 ms base and 2 s cap, with full jitter from item 28 and at most two retries. Fit delays and call timeouts inside an explicit total deadline. Honor a valid `Retry-After` as a minimum; if it exceeds the remaining interactive budget, return a recoverable response instead of sleeping longer. Durable jobs persist `available_at` for later retries; do not keep a Worker request alive while waiting minutes.
- **Current status.** No backoff function, deadline propagation or job retry scheduler exists. **Adoption trigger.** Implement alongside item 26; tune using latency and recovery measurements rather than accepting these sample settings as an SLO.
- **Acceptance evidence.** Fake-clock tests show capped growth, deadline exhaustion, cancellation, HTTP-date/delta `Retry-After`, malformed-header handling, and persisted job due times. Failure injection records actual elapsed time and downstream call count.

## 28. Jitter

- **Meaning and decision.** Randomize retry delays so clients do not retry simultaneously. Exponential delay alone can still create synchronized bursts. [AWS: exponential backoff and jitter](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/) **Plan.** Use full jitter, for example `random(0, min(cap, base × 2^retryIndex))`, subject to the deadline and any server-directed minimum delay. Add bounded spreading to reconnect polling. For recurring sweeps, use a stable per-shard offset or persisted due time where reproducibility helps; provider cron remains a coarse trigger. Inject clock and random sources for deterministic tests. Do not use randomness to alter command identity or business ordering.
- **Current status.** Planned only; no timer/retry code is present. **Adoption trigger.** Add with retries and polling/reconnect behavior; this is inexpensive application code, not a new service.
- **Acceptance evidence.** Seeded tests verify bounds and reproducibility. A many-client outage/recovery test compares per-second call peaks and completion latency against no jitter. Confirm background retries do not align on every minute boundary.

## 29. Circuit Breakers

- **Meaning and decision.** Temporarily stop calling a persistently unhealthy dependency, then allow limited recovery probes. A breaker differs from retrying: it avoids likely failures. Closed/open/half-open behavior requires explicit recovery rules. [Azure: circuit breaker](https://learn.microsoft.com/en-us/azure/architecture/patterns/circuit-breaker) **Plan.** Start with deadlines, bounded retries and concurrency limits. Add a per-dependency breaker only when repeated outages create avoidable latency/load. Count transient dependency failures, not user validation or version conflicts. An optional email/export integration can fail without blocking card work. A canonical database outage must fail writes clearly, never fabricate success. Worker global memory provides only opportunistic per-isolate state, not a shared worldwide breaker. Accept that limitation or coordinate through a deliberate provider adapter if global behavior is required.
- **Current status.** No breaker implemented; no external email/integration runtime exists. **Adoption trigger.** Measured repeated dependency failures or retry amplification; a shared breaker coordinator is deferred until its benefit exceeds its extra latency/complexity.
- **Acceptance evidence.** Inject sustained failure, open-state rejection, a bounded half-open probe, recovery and relapse. Observe reduced dependency calls and acceptable normal-request overhead. Test multiple runtime instances to expose the scope of breaker state.

## 30. Rate Limiting

- **Meaning and decision.** Control requests per actor/route/time window to protect latency, dependencies and usage allowances. An approximate abuse limit is different from a strict account quota. Cloudflare's Worker rate-limit binding is approximate and local to each location, not a globally exact counter. [Cloudflare rate limiting](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/) **Plan.** Define separate budgets for login/invitations, interactive writes, expensive searches and ordinary reads. Prefer authenticated actor/workspace keys; use IP only as an additional unauthenticated abuse signal because networks can be shared. Return 429 plus retry guidance. Keep strict business entitlements/paid-provider quotas in an atomic authority if introduced. Do not call a per-process map or approximate edge counter a global limiter. Limit concurrent work separately from requests per minute.
- **Current status.** API mentions 429 and per-user protection; no limiter or thresholds are deployed. **Adoption trigger.** Basic protection before public API/invitation exposure. Adopt strict distributed coordination only for a real global quota requirement.
- **Acceptance evidence.** Burst/concurrent/multi-instance tests distinguish local approximate and strict modes; unrelated users retain service; 429 retry behavior is bounded; revoked users never bypass auth through the limiter.

## 31. Load Balancing

- **Meaning and decision.** Route incoming traffic across healthy instances. Managed HTTP/serverless ingress may already provide this; an extra load balancer is not automatically useful. An AWS ALB can distribute traffic across targets and use health checks. [AWS ALB overview](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/introduction.html) **Plan.** Use the chosen platform's ingress initially. Do not put a separately managed ALB/NGINX tier in front of a Worker merely to tick the box. For replicated containers, configure managed ingress target health and drain behavior. Keep sessions, idempotency, authorization and jobs outside instance memory so routing does not require sticky sessions. Avoid routing write requests among unrelated regional primaries; database locality/consistency needs its own design.
- **Current status.** No deployed ingress, target group or load-balancing configuration. **Adoption trigger.** Platform ingress at first deployment; a dedicated load-balancing product only for multiple origins/instances or routing requirements not met by that ingress.
- **Acceptance evidence.** With at least two container targets when applicable, remove one under load and verify drain/routing, no lost committed commands, and bounded errors. For serverless, test the public route and record platform capability separately from application reliability.

## 32. Horizontal Scaling

- **Meaning and decision.** Add instances/consumers rather than make each one larger. This increases capacity only if the bottleneck can actually be parallelized. [Azure autoscaling guidance](https://learn.microsoft.com/en-us/azure/architecture/best-practices/auto-scaling) **Plan.** Keep API handlers stateless and consumers idempotent. Bound aggregate database connections and job concurrency; multiplying API instances does not increase a single primary's write capacity. Measure one busy board separately from many independent boards because its structure-version gate serializes conflicting moves. Worker distribution, Lambda concurrency and container replica count are provider controls with different limits. Define maximum scale/cost and scale-in drain rules before enabling aggressive autoscaling.
- **Current status.** Design intends stateless handlers; no replicated runtime, autoscale policy or load evidence exists. **Adoption trigger.** Sustained measured concurrency pressure with downstream headroom. Do not scale just because CPU briefly spikes or a marketing target predicts growth.
- **Acceptance evidence.** Compare one versus multiple workers/instances at fixed workload, recording throughput, p95/p99, DB saturation, version conflicts and cost. Kill a consumer after side effect/before acknowledgement and verify safe redelivery. Show that added capacity does not worsen the primary bottleneck.

## 33. Vertical Scaling

- **Meaning and decision.** Increase CPU/memory/capacity of an instance or database. It can be the simpler short-term response to a real resource ceiling, with deployment/cost tradeoffs. [Azure: vertical versus horizontal scaling](https://learn.microsoft.com/en-us/azure/architecture/best-practices/auto-scaling) **Plan.** First fix query plans, unnecessary scans, payload size and excess round trips. Then benchmark a larger container/database tier if CPU/memory remains limiting. A Worker has platform plan/resource limits rather than a user-selected VM size; upgrading plans is not equivalent to provisioning an arbitrary larger process. PostgreSQL and D1 capacity options differ, so the database comparison must include scaling limits, restore strategy and p95 under contention.
- **Current status.** No runtime size, paid tier or scaling evidence has been selected in this review; D1 is under reconsideration. **Adoption trigger.** Sustained resource saturation after application/query optimization and a favorable measured performance/cost result.
- **Acceptance evidence.** Run the same dataset/workload before/after size change; measure latency/throughput/resource use, connection limits, maintenance interruption and incremental cost. Rehearse rollback without assuming a compute rollback reverses a schema migration.

## 34. Reverse Proxies

- **Meaning and decision.** A proxy accepts client requests and forwards them to an origin, often handling TLS, routing and buffering. NGINX documents request/header forwarding and buffering controls; these settings can affect correctness as well as latency. [NGINX reverse proxy](https://docs.nginx.com/nginx/admin-guide/web-server/reverse-proxy/) **Plan.** Prefer one public origin and a simple `/api/*` route to the API before SPA fallback. Use platform TLS/ingress initially. Set request/body/time limits deliberately; do not return index.html for API failures. Trust forwarded client/IP/protocol headers only from known ingress. Mark authenticated API responses private/no-store. If SSE/WebSockets arrive later, configure buffering/idle timeouts explicitly; do not add them now. For a container migration, a standard managed ingress or NGINX adapter can preserve HTTP contracts.
- **Current status.** Routing is documented; no proxy or domain is deployed. **Adoption trigger.** Routing boundary at first hosted deployment; self-managed proxy only for an actual unsupported requirement.
- **Acceptance evidence.** Exercise TLS redirects, cookies, Origin/CSRF, spoofed forwarded headers, oversized bodies, API 404/500 JSON and SPA deep links through the real ingress. Measure latency added by each hop.

## 35. Message Queues

- **Meaning and decision.** A durable buffer decouples producers from consumers and smooths bursts; it does not remove downstream capacity limits. Cloudflare Queues and standard SQS can redeliver, and Service Bus explicitly settles received work. Design handlers to tolerate duplicates rather than claiming end-to-end exactly-once delivery. [Cloudflare delivery](https://developers.cloudflare.com/queues/reference/delivery-guarantees/), [SQS delivery](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/standard-queues-at-least-once-delivery.html), [Service Bus settlement](https://learn.microsoft.com/en-us/azure/service-bus-messaging/message-transfers-locks-settlement) **Plan.** Begin with the canonical database outbox and a bounded dispatcher. Add Cloudflare Queues, SQS or an Azure queue adapter for measured backlog, independent worker scaling or external delivery isolation. Publish small versioned events with IDs and references, not large private card/comment snapshots. Acknowledge only after durable idempotent handling; preserve retryable failure. Do not assume broker-specific ordering/deduplication features are interchangeable. Queue time must not sit on the interactive card-save critical path.
- **Current status.** Outbox schema exists; no managed broker, producer or consumer is implemented. **Adoption trigger.** Observed backlog/traffic isolation need or new external integrations; free-tier availability alone is not a trigger.
- **Acceptance evidence.** Duplicate, delayed, reordered and poison messages; crash after processing before ack; unavailable broker after DB commit; unauthorized/deleted referenced resources. Verify durable recovery and bounded fan-out.

## 36. Dead Letter Queues

- **Meaning and decision.** Quarantine messages/jobs that cannot succeed after bounded attempts, so one poison item does not retry forever. A DLQ needs retention, investigation and replay, not just a name. Cloudflare documents removal after retry exhaustion when no DLQ is configured. [Cloudflare DLQ](https://developers.cloudflare.com/queues/configuration/dead-letter-queues/) **Plan.** With database jobs, use a terminal/quarantined state with event ID, reason code, attempts and timestamps; avoid storing secrets in error text. If a broker is added, configure its DLQ explicitly, inspect its plan-specific retention and notify an operator before data expires. Replays retain logical event identity for dedupe but create an auditable replay attempt. Do not automatically loop a DLQ back into the source.
- **Current status.** No DLQ, quarantine transition, operational alert or replay command exists. Existing `outbox` columns are only a foundation. **Adoption trigger.** A quarantine path is required with the first durable dispatcher; a separate broker DLQ is required when that broker becomes part of the delivery path.
- **Acceptance evidence.** Inject an invalid versioned payload and sustained dependency failure; verify bounded attempts, quarantine, metrics/alert, successful fixed replay and no duplicate notification. Demonstrate the retention/recovery window, not a hard-coded universal four-day assumption; Free queue retention differs from paid defaults.

## 37. Background Workers

- **Meaning and decision.** Run deferred work independently of a user's request. A long-running container worker and a short scheduled/serverless invocation have different lifecycles. Workers `waitUntil()` can extend an HTTP invocation for up to 30 seconds after response/disconnect; unfinished work can then be cancelled. [Cloudflare context](https://developers.cloudflare.com/workers/runtime-apis/context/) **Plan.** Persist pending work before returning success. Use a bounded dispatcher that atomically claims due jobs with a lease/fencing token, performs idempotent work, then marks completion conditionally on that token. Expired leases permit recovery. A container may poll continuously with bounded idle sleeps; Worker/Lambda/function adapters drain a bounded batch per invocation. `waitUntil()` may make a best-effort immediate kick, but durable scheduled recovery remains authoritative. No required side effect should depend only on an unawaited promise.
- **Current status.** Outbox attempts/availability/lease fields exist; claiming, fencing, execution and recovery are unimplemented. **Adoption trigger.** First asynchronous mention/outbox delivery. Start with one dispatcher implementation and provider entry adapters, not a fleet of microservices.
- **Acceptance evidence.** Two dispatchers race; one crashes mid-job; a lease expires; a stale worker finishes late. Verify one logical effect and no stale completion overwrite. Measure job age and request latency independently.

## 38. Job Scheduling

- **Meaning and decision.** Trigger recurring or due work without requiring a browser to be open. A scheduler's invocation is not proof the job ran once or completed. Cron syntax/timezone/retry semantics differ by platform. [Workers Cron](https://developers.cloudflare.com/workers/configuration/cron-triggers/), [EventBridge Scheduler direction](https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-run-lambda-schedule.html), [Azure timer trigger](https://learn.microsoft.com/en-us/azure/azure-functions/functions-bindings-timer) **Plan.** Use a small recurring recovery sweep for due outbox rows; a one-minute cadence is a prototype option, not an accepted notification-lag target. Persist UTC `available_at`, last success, execution duration and oldest due job. Platform cron invokes the same bounded drain operation. Protect overlap with atomic leases; use logical period/run IDs for periodic jobs. Cloudflare schedules use UTC; workspace-local reminders need explicit timezone/DST conversion if later approved. Missed ticks require scanning due state, not assuming every tick happened. Prefer EventBridge Scheduler over legacy scheduled rules on AWS.
- **Current status.** Scheduled sweep is proposed; no cloud schedule or handler exists. **Adoption trigger.** First durable dispatcher/recovery path; reminders and maintenance jobs are added only when scoped, with separate retention/deletion policy.
- **Acceptance evidence.** Duplicate/overlapping/missed invocation, provider delay, invalid job, expired lease and daylight-saving boundaries for any future local-time work. Record last successful drain and actual delivery lag.

## 39. Event-Driven Architecture

- **Meaning and decision.** React to committed business events rather than coupling every side effect to the caller. Queue-based buffering can isolate bursts, but asynchronous paths introduce delivery lag and failure recovery. [Azure queue-based load leveling](https://learn.microsoft.com/en-us/azure/architecture/patterns/queue-based-load-leveling) **Plan.** Use a small local event vocabulary such as `comment.created` for mention delivery, with event ID, schema version, workspace/entity reference, occurrence time, causation/operation ID and trace context. Keep core card mutations synchronous and transactional; publish only committed events. Consumers validate versions, tolerate duplicates and apply authorization when reading referenced content. Do not turn every function call into an event or add Kafka/EventBridge/Event Grid for the first board flow.
- **Current status.** Activity/outbox concepts and tables exist; there is no event publisher, consumer registry or schema compatibility test. **Adoption trigger.** Committed mention delivery now; a managed event bus later only when multiple independently operated consumers or routing requirements justify it.
- **Acceptance evidence.** A rolled-back command emits nothing; duplicate/out-of-order events do not corrupt state; unknown schema versions quarantine safely; every accepted event reaches a documented terminal outcome. Test with two independent consumers before claiming fan-out support.

## 40. Webhook Verification

- **Meaning and decision.** Authenticate incoming provider events before spending application work or accepting their claims. GitHub signs webhook payloads with HMAC-SHA256 and recommends verifying the original payload. [GitHub verification](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries) **Plan.** Webhooks are outside the current board MVP. When an integration is approved, build a provider-specific adapter: bound body size, retain original bytes, verify signature with Web Crypto/approved library before parsing/re-serialization, map installation/resource to the authorized workspace, and persist a durable dedupe receipt. Rotate secrets deliberately. Verify a timestamp/replay window only when the provider actually signs one; GitHub's HMAC alone is not a universal signed-timestamp scheme. Use delivery IDs plus payload/signature digest policy for replay defence. An OAuth browser callback is not interchangeable with a webhook.
- **Current status.** No inbound webhook endpoint/provider exists. GitHub source hosting does not itself require a product webhook. **Adoption trigger.** First approved external event integration; not before.
- **Acceptance evidence.** Official test vectors, one-byte body changes, missing/malformed/wrong signature, duplicate delivery, changed whitespace, wrong installation/workspace, stale timestamp where supported and secret rotation. Verify rejection before domain side effects.

## 41. Webhook Retries

- **Meaning and decision.** Recover external event delivery separately from core API retries. Provider policies differ: GitHub explicitly does **not** automatically redeliver failed deliveries. [GitHub failed deliveries](https://docs.github.com/en/webhooks/using-webhooks/handling-failed-webhook-deliveries) **Plan.** For incoming hooks, verify and durably accept/dedupe, then respond within the provider deadline; process later from durable state. If admission fails, return failure rather than a success that loses the event. Add provider-specific redelivery/reconciliation if required; never assume every provider retries. Outbound hooks, if added, use an outbox, stable delivery ID, bounded exponential backoff/jitter, per-destination concurrency, status classification, expiry and quarantine. Recheck authorization when generating payloads. User-configured destinations require an explicit safe egress policy before becoming a product feature.
- **Current status.** Neither inbound reconciliation nor outbound webhook delivery is implemented or in MVP scope. **Adoption trigger.** An approved webhook integration with a written delivery/reconciliation contract. A scheduler/broker retry count alone does not satisfy that contract.
- **Acceptance evidence.** Receiver downtime, acceptance commit followed by lost response, provider redelivery, 429/503, permanent 4xx, timeout and poison target. Prove one logical effect and an inspectable final outcome.

## 42. Eventual Consistency

- **Meaning and decision.** Some views/side effects may lag a committed source of truth. Declare where lag is acceptable; do not use it as an excuse for weak authorization or lost card writes. Asynchronously separate read/write projections require synchronization and can lag. [Azure CQRS consistency](https://learn.microsoft.com/en-us/azure/architecture/patterns/cqrs) **Plan.** Card saves, ordering, revision checks, membership enforcement and idempotency operate against canonical state. Notifications and other clients' polling views may lag. Return canonical versions after writes so the acting client does not immediately replace success with older data. Expose refreshing/offline state and measure outbox age plus poll convergence. A revoked member's next API/notification read must fail even if an old event/view exists. Introduce replica/cache reads only after defining read-after-write and revocation behavior.
- **Current status.** Polling/outbox consistency is documented, but no client synchronization or replica/cache behavior has been tested. **Adoption trigger.** This boundary must be defined with the first polling/async feature; additional eventual read stores remain deferred until measurements justify them.
- **Acceptance evidence.** Pause dispatcher/polling, then resume and observe convergence; deliver an old version after a new one; revoke membership while notifications are pending. Prove no overwrite, unauthorized exposure or permanent missing effect.

## 43. Distributed Transactions

- **Meaning and decision.** Coordinate one business operation across separate transactional systems. There is no automatic atomic commit between a database, queue, email provider and Durable Object. Sagas use local steps and compensation rather than pretending all steps share one ACID transaction. [Azure saga pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/saga) **Plan.** Keep first-release card/comment/activity/receipt/outbox changes in one canonical database transaction. Send external effects after commit via item 44. Do not introduce two-phase commit or split the board into database-per-service microservices. If a future multi-service workflow needs compensation, model its state machine, retries, timeout, manual recovery and idempotent compensation explicitly. Undoing a card move is a new version-checked business command; recalling an already delivered email is generally not a valid compensation.
- **Current status.** No distributed workflow exists; local SQLite guard/rollback checks do not prove remote D1/PostgreSQL behavior or cross-service atomicity. **Adoption trigger.** Only an approved operation genuinely spanning independent transactional services. Otherwise preserve the simpler single-database boundary.
- **Acceptance evidence.** For current scope, forced local failure must leave no partial data/event/receipt. For any future saga, inject failure after each step and prove compensation/manual terminal states, duplicate handling and reconciliation.

## 44. Outbox Pattern

- **Meaning and decision.** Save a business change and durable event intent in the same database transaction, then deliver the event separately. This closes the “database committed but publication failed” gap, while still requiring idempotent consumers. [AWS transactional outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html) **Plan.** Commit comment, mentions, activity, receipt and outbox together. Dispatcher claims due rows atomically with expiry and fencing, processes a bounded batch, and marks completion only for its active claim. Unique event/recipient keys prevent duplicate inbox entries. Treat publish-success/mark-failed as a duplicate-on-retry case. Track pending/leased/complete/quarantined, attempts, next time, oldest age and sanitized error. With the same database, notification insertion and job completion may share a transaction; remote delivery cannot. Recheck recipient access and current content policy before exposing a notification.
- **Current status.** Outbox schema/index/lease/attempt fields and notification uniqueness exist. No dispatcher, lease race handling, retry policy or actual provider transaction proof exists. **Adoption trigger.** Required with asynchronous mention delivery. A broker is optional; the transactional intent record and recovery are not.
- **Acceptance evidence.** Crash before commit, after commit, after side effect/before completion; concurrent claim; expired/stale lease; duplicate event; poison row; denied recipient. Show durable recovery and one logical notification.

## 45. CQRS

- **Meaning and decision.** Separate command/write logic from query/read shapes; this does not require two databases. Azure describes a basic approach using separate models in one data store. [Azure CQRS](https://learn.microsoft.com/en-us/azure/architecture/patterns/cqrs) **Plan.** Use explicit commands such as move/archive/post-comment and lean paginated board/card-summary queries, all on the same canonical database initially. Write handlers own invariants; reads return DTOs appropriate to the UI without loading entire comment histories. Call this separation of command/query responsibilities, not a delivered distributed CQRS system. Add indexes/projections in the same store before introducing a separate search/read service. If an async read store is later justified, require event replay, lag metrics, rebuild/cutover and permission propagation.
- **Current status.** API contract separates moves from generic field PATCH and outlines compact/detail reads. No runtime handlers or independent read model exists. **Adoption trigger.** Lightweight code organization from the first implementation. Separate databases/projection infrastructure only after indexed canonical reads demonstrably miss goals.
- **Acceptance evidence.** Verify bounded query count/payload and correct filters/counts/pagination; compare query plans and p95 against a generic full-object implementation. Reads enforce current access; writes cannot bypass command invariants.

## 46. Event Sourcing

- **Meaning and decision.** Make an ordered event stream the authoritative state and rebuild present state by replaying it. An audit/activity table next to mutable cards is not event sourcing. Microsoft stresses its schema/replay/concurrency complexity and that ordinary state storage is sufficient for most systems. [Azure event sourcing](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing) **Plan.** Do not adopt it for the first Flowboard release. Keep current relational card state plus immutable activity and durable outbox intent. A requirement to review card history or undo a move does not establish a need to reconstruct every aggregate from events. Reconsider only if reliable point-in-time domain reconstruction becomes a product requirement that ordinary audit/backup designs cannot satisfy.
- **Current status.** Not implemented and intentionally deferred. Existing `activity_events` must not be advertised as a complete replayable source of truth. **Adoption trigger.** An explicit reconstruction/history requirement and proven operational capacity to maintain event versions, replay and recovery; not speculative performance improvement.
- **Acceptance evidence if adopted.** Rebuild from empty state, compare deterministic projections, migrate old event schemas, handle invalid historical events, enforce stream concurrency and retention/privacy policy, and rehearse recovery time at real data volume.

## 47. Backpressure

- **Meaning and decision.** Slow or reject incoming work when consumers/dependencies cannot keep up, instead of allowing unbounded memory, connections, queue age or retries. A queue smooths a burst; it does not fix sustained overload. [Azure load leveling](https://learn.microsoft.com/en-us/azure/architecture/patterns/queue-based-load-leveling), [Cloudflare consumer concurrency](https://developers.cloudflare.com/queues/configuration/consumer-concurrency/) **Plan.** Bound request body/page sizes, concurrent dependency calls, job batch size, producer fan-out, retry budget and dispatcher concurrency. Pause/dedupe hidden/overlapping polling and debounce member search. Set managed consumer concurrency to protect measured DB/upstream capacity rather than allowing maximum platform fan-out. Stop claiming more jobs before invocation deadline; let unclaimed work stay durable. Use 429 for actor limits and an explicit temporary-unavailable response when system admission is exhausted; preserve drafts.
- **Current status.** Contract pagination/field limits exist on paper; no admission control or consumer saturation measurements. **Adoption trigger.** Basic bounds before public release; tune fairness/consumer controls with observed saturation. Add capacity only when the protected dependency has headroom.
- **Acceptance evidence.** Sustain arrivals above drain capacity: memory/connection use stays bounded, overload is visible, interactive latency remains protected and backlog later drains. Verify fairness so one workspace does not starve others and that alerts track oldest job age, not only count.

## 48. Graceful Shutdown

- **Meaning and decision.** Stop accepting new work, finish or safely hand off current work, then exit within the platform's deadline. Containers often receive TERM followed by forced termination; serverless invocations do not provide the same application-controlled process lifecycle. [Kubernetes termination semantics](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/), [Lambda lifecycle](https://docs.aws.amazon.com/lambda/latest/dg/lambda-runtime-environment.html), [Worker invocation limits](https://developers.cloudflare.com/workers/platform/limits/) **Plan.** For a Node/container adapter, handle termination once, become unready, stop job claims/listening, drain bounded in-flight work, close resources, and exit before configured grace expires. Use durable idempotency/leases because SIGKILL still happens. For Workers, finish critical writes before response, persist deferred work, bound execution, and recover expired claims; do not invent a SIGTERM handler or depend on an immortal global loop. `waitUntil()` is a bounded execution extension, not a durable shutdown hook. Lambda environments may freeze/recycle; generic Node signal behavior is not its reliability contract.
- **Current status.** No container/Worker/Lambda runtime or shutdown code exists. **Adoption trigger.** Lifecycle-specific implementation before deploying that runtime; do not require a container orchestrator just to implement graceful behavior.
- **Acceptance evidence.** Terminate mid-request/mid-job, deploy a new revision, disconnect a client and force invocation cancellation. Verify bounded termination, safe retry/lease recovery and no duplicate committed effect. Capture evidence separately for each runtime adapter.

## 49. Health Checks

- **Meaning and decision.** Separate “process can respond,” “instance can receive traffic,” and “startup is complete.” Readiness failure should not automatically become a restart loop. Kubernetes documents the different probe purposes and that failed readiness removes a pod from service traffic. [Probe guidance](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/) **Plan.** Container option: cheap local liveness, bounded readiness for configuration/required dependencies, and startup allowance where necessary. Do not put a flaky database test into liveness and restart every instance during a database outage. Worker option: no process-killing liveness endpoint; use external synthetic route/dependency checks, platform errors and outbox last-success/age. A simple `/health` proving routing is different from a protected readiness/dependency diagnostic. Do not expose credentials, detailed infrastructure or private data through public checks. Use cached/bounded dependency probes to avoid monitoring causing overload.
- **Current status.** No health endpoints, synthetic monitor or alert wiring exists. **Adoption trigger.** Before first hosted environment; deeper probes only for dependencies actually in the release.
- **Acceptance evidence.** Distinguish wrong route, deadlocked process, slow startup, database outage, bad config and stuck dispatcher. Show correct alert/routing behavior without restart storms; prove recovery clears the incident. A single HTTP 200 is not a successful card-save test.

## 50. Distributed Tracing

- **Meaning and decision.** Correlate one operation across HTTP, database/dependency calls and deferred work to explain where latency/failure occurs. W3C defines trace context; OpenTelemetry describes propagating it across services. [W3C Trace Context](https://www.w3.org/TR/trace-context/), [OpenTelemetry propagation](https://opentelemetry.io/docs/concepts/context-propagation/) **Plan.** Start with structured logs and request/operation/event IDs plus route/DB timing. Add sampled spans for inbound request, authorization, DB command and outbox handling; use W3C `traceparent` propagation and appropriate links for delayed jobs. Keep business idempotency IDs distinct from trace IDs. Put provider exporters behind an adapter so OTLP-compatible telemetry can migrate across clouds. Validate the chosen SDK/exporter in Workers separately from Node. Bound sampling, payload and flush cost; telemetry failure must not break a card save. Never put comment bodies, session tokens, email addresses or user-controlled baggage into unrestricted trace attributes.
- **Current status.** Request IDs are documented; no instrumentation/exporter/dashboard has run. **Adoption trigger.** Structured correlation/timing from the first API; sampled distributed spans when the runtime supports a verified low-overhead exporter and when dependency/async paths need diagnosis.
- **Acceptance evidence.** One synthetic comment spans HTTP → DB → outbox → inbox with searchable IDs; a forced slow dependency is distinguishable from cold start/DB wait. Test sampling, failed exporter, cancellation and privacy redaction; measure CPU/p95/cost overhead on the selected plan. Trace context is correlation, not authorization.

## Suggested implementation order and review gates

1. **First working networked slice:** atomic revision/idempotent writes, dependency deadlines, bounded retry/backoff/jitter, page/body/concurrency bounds, basic rate protection, structured timings/IDs, explicit error recovery. Benchmark database/runtime candidates before freezing deployment decisions.
2. **First asynchronous mention slice:** durable outbox, fenced leases, duplicate-safe inbox insertion, bounded drain, quarantine, recovery schedule, oldest-age/last-success visibility and failure-injection evidence. A managed broker is optional.
3. **First hosted slice:** correct ingress/TLS/API routing, private responses, lifecycle-specific cancellation/shutdown, meaningful synthetic/health checks, account-specific free-allowance/cost review and recovery rehearsal. Local SQLite checks remain separate from provider-runtime proof.
4. **Only after measurements:** increase runtime/database capacity, add broker/DLQ consumers, shared circuit-breaker coordination, separate read projections, or faster event transport. Each needs a stated bottleneck, expected benefit, benchmark and rollback plan. Distributed transactions and event sourcing remain deferred absent an explicit business need.
