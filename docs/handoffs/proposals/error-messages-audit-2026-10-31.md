# Error messages audit: every failure should say why and what to do

Date: 2026-10-31. Mode: read-only research (no source edited, nothing run against any database or deployed).
Evidence tags: **V** = verified by reading the cited code path; **I** = inferred (not run, or only part of the path read).
Paths are relative to the repo root. `api` = `apps/api/src`, `web` = `apps/web/src`.

## 1 Summary in plain English

- The API can raise about **104 distinct error codes** (about 63 plain `'CODE'` literals, 15 passed as bare arguments, 15 spreadsheet-import codes, 10 image-validator codes, plus health and transport codes; **I**, counted by grep over `HttpError.*`, `new HttpError(` and the helpers in `api/http/errors.ts`). The shared contract lists only **21** (`packages/contracts/src/common.ts:3-26`), so roughly 80 codes have no entry in any shared list and no test that a message exists.
- The web app turns an error into text in one place: `describeError` (`web/lib/errors.ts:7-18`). It has purpose-written text for about **14 codes** (quota, name required, read-only, expired invitation, stale, 429, assignee refusal, board required, config, and 10 image codes inside the upload path only). Only about **6** of those meet the style bar of "what happened, why, what to do".
- About **90 codes fall through** to either one of four generic sentences ("You do not have permission to do that.", "Your session ended. Sign in again.", the stale sentence) or **the raw server message shown verbatim** (`errors.ts:15`, **V**). Raw text includes "Internal server error.", "Validation failed: title: String must contain at least 1 character(s)", "Idempotency key collision with different request payload.", "XML External Entity (XXE) declaration detected in …" and `HTTP request failed with status 502`.
- Several messages are **wrong or misleading**: any board-archived write says "This project is archived" (`quota-messages.ts:95`); the assignee refusal says "They do not have access to this board" even when the real reason is that the person is a Viewer or has left the project (`assignees.ts:63`); the Google sign-in failure shows a raw JSON page because the API throws on a top-level browser navigation (`api/http/routes/google-auth.ts:118-184`).
- **Top 5 worst:** (1) Google sign-in failures render raw JSON in the browser; (2) a card whose column was deleted can never be restored from Trash and the message is raw (`RESTORE_DESTINATION_REQUIRED`, `web/app/trash/page.tsx:57`); (3) all 403s say the same "You do not have permission", with no role or remedy; (4) every error toast vanishes after 4.5 s and speaks politely, not as an alert (`web/components/ui/toasts.tsx:26,62`); (5) any `VALIDATION_ERROR` (422) shows the raw zod sentence or a developer sentence, and 5xx shows "Internal server error.".

**Board access is Owner-only, not Owner or Manager** (**V**: `api/http/routes/board-grants.ts:44`, `api/adapters/board-grants-foundation.ts:83`, button shown only to the Owner at `web/app/people/page.tsx:88`). Copy that tells a Manager "Give them access in People" would send them to a button they cannot see. See open decision D1.

## 2 Inventory table

How to read: "UI today" is the exact string the user sees, with `[file:line]`. "Roles" says who gets which version. `{name}`, `{board}`, `{project}`, `{limit}` come from `error.details` or data the client already holds. Status is the HTTP status the server sends. Proposed copy is **title / sentence(s) / remedy button**.

Legend for generic fallbacks: **G403** = "You do not have permission to do that." (`errors.ts:12`); **G401** = "Your session ended. Sign in again." (`errors.ts:11`); **GSTALE** = "Someone else changed this. The latest version has been loaded; try again." (`errors.ts:13`); **RAW** = `error.message` verbatim (`errors.ts:15`).

## 5 Class handling (offline, 401, 403, 404, 409, 413, 422, 429, 5xx)

One function maps `(status, code, details, role, ctx)` to `{ title, body, action?, severity, retryable }`. These are the **class defaults** used when a code has no specific entry.

**Accessibility and behaviour rules for every error surface**

1. **Announce:** inline errors use `role="alert"` (already common); toasts that carry an error use a separate assertive region `role="alert"`, not the polite status region (`toasts.tsx:62`).
2. **Focus:** after a failed submit, move focus to the error summary or the first invalid field (`tabIndex={-1}` target, as already done for the assignee failure, `drawer:383,274`). Do not steal focus from a field the user is typing in on a background poll failure.
3. **Persistence:** an error stays until the user acts (edits the field, dismisses, retries, or leaves). An error that carries a remedy button never auto-dismisses. Success toasts may keep 4.5 s. Pause timers on focus as well as hover (`toasts.tsx:34-35`).
4. **Save bar:** after a failed save the bar reads "Couldn’t save. {reason}" in the danger colour with a **Try again** button; it never reads "Unsaved changes" while `save.isError`. It returns to "Unsaved changes" only after the user edits again, and the alert text stays until then. (Drawer logic at `drawer:431` is right; the reason line and retry button are missing.)
5. **Buttons:** primary action re-enabled in `finally`; during a 429 countdown it is disabled with a visible timer and `aria-describedby` on the message.
6. **Layout:** at 360 to 430 px wide, the message sits above the footer actions, wraps, is not clipped by the drawer footer (the drawer error is inside the scroll area at `drawer:425`, so it can be below the fold: scroll it into view like `drawer:384`), with the remedy button full width.
7. **Language:** sentence case, no "please", no "successfully", no exclamation marks; title ≤ 6 words; each sentence ≤ 25 words; no codes, ids, status numbers, bytes or milliseconds.
8. **Request id:** show "Reference: {requestId}" with a copy button only for 5xx and unknown codes, inside a `<details>` or small text.
