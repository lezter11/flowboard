# Bounded XML performance backports for the Linux release gate

Status: implementation selected after diagnostic proof; fresh product review and Linux CI remain pending. Baseline `77a9fbb`, user requires unchanged security limits and conserving the 2,000-minute monthly Actions allowance.

A legal 200-row workbook with 20,000 escaped ampersands per description expands to approximately 20 MB of XML. Linux CI rejected it at the existing 1,000 ms parser budget. Local Worker plus PostgreSQL reproduces the same error under an explicit 0.75 CPU quota under ARM64 pressure; this is not GitHub x64 hardware equivalence. Two application-native scans are semantically equivalent but alone pass only 2/5 pressure samples. Source profiling finds costly regex MatchArray allocation in the validator and per-unit text concatenation in the ordered parser.

Choose four small equivalent optimizations: native raw-scalar/structural scans in import-xml, an ASCII named-reference predicate and bulk plain-text accumulation in the existing pinned fast-xml-parser 5.11.2 ESM source. Full XMLValidator grammar and ordered tree construction stay active. No entity masking, parser budget/cap changes, input reduction or atomicity changes. Diagnostic B passes 5/5 fresh full original Worker/PG fixtures; a separate cold parser run is 655 ms versus unchanged 1,000 ms. A total of 4,230 parser output, Symbol metadata and callback comparisons and existing 122 parser cases support equivalence, alongside independent source reasoning. These are diagnostic evidence; product verification must repeat on actual installed backports.

Alternatives: a full SAX adapter changes namespace/entity/text/error/metadata semantics and requires a larger review. Primary-source research found saxes archived and sax-js strict mode not fully well-formedness strict. An upstream release without equivalent measured fixes does not solve this incident by itself. Increasing budgets or removing accepted fixtures changes the agreed safety/feature boundary and is excluded.

The local backport has a maintenance cost. Its tracked manifest binds the original npm tarball/version/integrity, package metadata/ESM entry/license, exact original→patched hashes and tiny patch files. Install-time apply is idempotent and rejects unknown bytes before writes. Tests/builds verify; offline or ignore-scripts installs explicitly apply then verify. Requests never write dependency files or fetch patches. Worker source maps must contain both exact patched ESM sources and no FXP CJS source; Node must select the pinned ESM entry. CJS stays upstream and is outside the selected acceleration path. No claim that npm supplied modified bytes or that dependency advisories prove local-patch correctness.

Future upgrades must rebase/remove these backports with independent semantic/security/runtime evidence; changing expected hashes is not approval. Prefer removing the local maintenance layer when an independently reviewed upstream release provides equivalent performance and behavior. Keep the full MIT notice and provenance. Code, verification and release status live in [the frozen repair criteria](../reviews/HOSTED-MCP-20261104/linux-xlsx-repair/CRITERIA.md) and [PROGRESS](../../PROGRESS.md); production remains excluded.
